- 大学や専門学校でシステム開発を学び始めた学生

# 第1部: 仕様書とは何か ― 全体像の理解

## 第1章: なぜ仕様書が必要なのか

### 1.1. いきなりコードを書くと何が起きるか

プログラミングを始めたての人は、まずコードを書き始めがちです。
しかし、いきなりコードを書き始めると、次のような問題が起きます。

1. **何を作ればいいか曖昧になる**: 「コンビニのレジを作りたい」と言っても、
   商品検索？ 会計計算？ レシート？ どこまで作れば「完成」なのかが分かりません。
2. **途中で方針が変わる**: 「あれ、税率は8%と10%で2種類あるんだ」「お釣りの計算は切り捨てなのか切り上げなのか」
   という議論が開発中に発生し、作り直しが発生します。
3. **他人と作業が被る**: チーム開発の場合、Aさんがデータベースを作っている間にBさんが画面を作ろうとすると、
   「データベースのテーブル構造がまだ決まっていない」という問題が起きます。

### 1.2. 仕様書は「設計図」である

仕様書は、建築の「設計図」に相当します。

```
建築の例:
  注文者（クライアント）→ 「3LDKの家が欲しい」
  建築士 → 設計図を描く
  大工   → 設計図に従って家を建てる

ソフトウェアの例:
  依頼者（クライアント）→ 「コンビニのレジシステムが欲しい」
  エンジニア → 仕様書（設計図）を書く
  開発者     → 仕様書に従ってコードを書く
```

仕様書があることで、「何を作るのか」「どう作るのか」「完成の基準は何か」が明確になります。

### 1.3. 本プロジェクトの仕様書の特徴

本プロジェクトの仕様書は「**Spec指向開発**」と呼ばれる手法に基づいています。
これは、以下の特徴を持つ開発手法です。

1. **仕様を先に書く**: コードを書く前に、まず仕様書を書く
2. **4段階に分ける**: 大枠→詳細→技術計画→タスク分解の順で進める
3. **上流から修正する**: 途中で仕様が変わった場合、上流の仕様書から修正を始める
4. **AIがコードを書く**: 仕様書が決まれば、AI（または人間）が仕様に従ってコードを書く

## 第2章: 仕様書の全体マップ

### 2.1. 4ステップ構造

本プロジェクトの仕様書は、大きく分けて4つのステップに分かれています。

```
Step1: プロジェクト憲法     「絶対に守るルール」
   ↓
Step2: 要件定義・外部設計   「なぜ必要か」「何ができるようになるか」
   ↓
Step3: 内部設計・技術計画   「どうやって実装するか」
   ↓
Step4: タスク分解           「一つ一つ何をするか」
```

それぞれのステップには「メインドキュメント」と「補助ドキュメント」があります。

### 2.2. ドキュメント間の依存関係

```
step0000（全体マニュアル）
  │
  ├── step0100（プロジェクト憲法）
  │     └── step0101（開発履歴）
  │
  ├── step0200（要件定義）
  │     ├── step0201（業務ルール）
  │     ├── step0202（業務フロー）
  │     ├── step0203（非機能要件）
  │     ├── step0204（UI設計）
  │     ├── step0205（機能仕様）
  │     ├── step0206（軽減税率拡張）
  │     ├── step0207（レシート拡張）
  │     └── step0208（サービスアーキテクチャ）
  │
  ├── step0300（技術計画）
  │     ├── step0301（技術計画詳細）
  │     ├── step0302（テスト戦略）
  │     ├── step0303（テスト計画）
  │     ├── step0304（運用・配置計画）
  │     ├── step0305（リスクレジスター）
  │     ├── step0306（UAT計画）
  │     ├── step0307（ロールバック手順）
  │     ├── step0308（データ辞書）
  │     └── step0309（トレーサビリティ行列）
  │
  └── step0400（タスク管理リスト）
```

**重要**: 仕様書は上から下へ順番に書きます。
下の階層の仕様書を書いてから上の階層に戻って書き直すのは、原則として避けるべきです。

### 2.3. Who/When/What の整理

| ステップ | 書く人 | 書くタイミング | 書く内容 |
|----------|--------|--------------|----------|
| Step1 | 人間 | プロジェクト開始時（1回のみ） | 技術スタック、コード規約 |
| Step2 | 人間 | Step1確定後 | Why + What（なぜ必要か、何ができるか） |
| Step3 | AI + 人間のレビュー | Step2確定後 | How（どう実装するか） |
| Step4 | AI（自動生成） | Step3承認後 | タスク分解チェックリスト |

## 第3章: step0000_order_specification_preparation.md（仕様書作成順序マニュアル）

### 3.1. このドキュメントの役割

これは「**マニュアルのマニュアル**」です。
他のすべての仕様書を「どんな順番で」「どんな目的で」書くかを定義する、仕様書自身の説明書です。

### 3.2. 内容の解説

本文書は以下の要素で構成されています。

#### （1）作成順序フロー

```
Step1 → Step2 → Step3 → Step4 の順で進める
```

このフローは「ウォーターフォール型開発」に似ていますが、
本プロジェクトではこのフローに従って仕様書を作成し、
その仕様書に従ってAIがコードを生成するという点で異なります。

**初心者へのヒント**: ウォーターフォールとは？

ウォーターフォールとは、水が階段を落ちるように、
上のフェーズから下のフェーズへと一方向に進む開発手法です。
各フェーズが完了してから次のフェーズに進みます。
対義語として「アジャイル（俊敏型）」があり、こちらは短期間で繰り返し開発します。

本プロジェクトでは「仕様書の作成」にウォーターフォールの考え方を適用しています。
仕様書は上から下へ順番に書き、途中で上流に戻ることは原則ありません。

#### （2）各ステップの定義

各ステップには以下の情報が表格で定義されています。

| 項目 | 内容 |
|------|------|
| 対象ファイル | どのファイルに書くか |
| タイミング | いつ書くか |
| 作成者 | 誰が書くか（人間 or AI） |
| ウォーターフォールとの対応 | 伝統的な開発工程のどのフェーズに相当するか |

**初心者へのヒント**: なぜ表格で定義するのか？

表格は情報を整理して見せるのに最適です。
項目と内容が左と右に並ぶので、「何についての情報か」が一目で分かります。
仕様書で表格を使うことは非常に一般的で、このプロジェクトでもすべての仕様書で表格が活用されています。

#### （3）完成条件（チェックポイント）

各ステップには「完了条件」が定義されています。

```
### Step2 完了条件
- [X] step0200_spec.md が存在し、Why + What が記述されている
- [X] 受け入れ基準（AC）がすべて定義されている
- [X] スコープ外が明確に定義されている
```

チェックボックス `[X]` は完了、`[ ]` は未完了を表します。

**初心者へのヒント**: 完了条件を先に定義するメリット

完成の基準を先に定義しておくことで、「いつやればいいのか」が明確になります。
テストと同じで、「何を検証するか」を先に決めておくのです。

#### （4）ルール

本文書には5つのルールが定義されています。

1. **Stepの順序は厳守する**: 飛ばしてはいけない
2. **Step3は人間のレビュー必須**: AIが作成しても人間がチェックする
3. **Step4は自動生成**: AIが自動でタスクを分解する
4. **仕様変更時は上流から修正**: 下の仕様書だけ直すのは禁止
5. **プロジェクト憲法は全員で共有**: 例外なく守る

### 3.3. 自分で書く場合のポイント

- 「なぜこの順番なのか」を最初に説明する
- 各ステップの「書き手」と「タイミング」を明確にする
- 完了条件は具体的に書く（「適切に」ではなく「80%以上のカバレッジが達成されていること」のように）
- ルールは5つ以内に絞る（多すぎると覚えられない）

## 第4章: Step1 ― プロジェクト憲法（step0100_constitution.md）

### 4.1. このドキュメントの役割

プロジェクト憲法は、プロジェクトの開始時に1回だけ作成するドキュメントです。
「**絶対に破ってはいけないルール**」を定義します。

### 4.2. 内容の解説

本文書は非常に短い（27行）ですが、これには理由があります。
プロジェクト憲法は「**最小限かつ絶対的なルール**」だけを書くからです。

#### （1）絶対的な技術スタック

```
- 言語: C# (.NET 8.0)
- UIフレームワーク: WPF
- アーキテクチャ: MVVM (CommunityToolkit.Mvvm)
- データベース: SQL Server (LocalDB)
- ORM: Entity Framework Core (コードファースト)
```

これは「このプロジェクトではこれらの技術だけを使う」という宣言です。

**初心者へのヒント**: なぜ技術スタックを先に決めるのか？

技術スタックを先に決めることで、以下の問題を防げます。

- AさんはC#で、BさんはPythonで書いている → マージできない
- 途中でフレームワークを変える → 作り直しが発生する
- テスト方法が不明確 → 品質管理ができない

技術スタックは「建築でいう鉄筋か木造か」のような基本設計です。
ここが決まっていないと、何も始まりません。

**初心者へのヒント**: それぞれの技術の意味

- **C# (.NET 8.0)**: プログラミング言語とその実行環境
- **WPF**: Windowsのデスクトップアプリの画面を作るフレームワーク
- **MVVM**: デザインパターン。画面(Model)・データ(Model)・ロジック(ViewModel)を分離する考え方
- **SQL Server LocalDB**: データベース。商品情報や取引記録を保存する
- **Entity Framework Core**: C#からデータベースを操作するためのライブラリ

#### （2）実装・コード規約

```
- すべてのUIロジックはViewModelに記述する
- 変数名やメソッド名はPascalCase、camelCaseに従う
- DbContextの寿命を適切に管理する
```

**初心者へのヒント**: コード規約とは？

コード規約は「コードの書き方のルール」です。
たとえば、変数名は「`itemCount`」のようにcamelCaseで書く、
クラス名は「`ProductService`」のようにPascalCaseで書く、
というルールです。

なぜこれが重要か？

- **読みやすさ**: ルールが決まっていると、誰が書いたコードでも同じように見える
- **保守性**: 6ヶ月後に自分が見返しても理解しやすい
- **チーム開発**: チーム全員が同じルールで書くことで衝突がない

### 4.3. 自分で書く場合のポイント

- **短く書く**: プロジェクト憲法は「最小限のルール」だけを書く
- **絶対的なルールだけを書く**: 「できれば」は書かない、「必ずそうする」ことだけ書く
- **技術スタックを明確に**: 「何を使うか」と「何を使わないか」の両方を書く
- **コード規約は10個以内に**: 多すぎると守れない

## 第5章: step0101_development_history.md（開発履歴）

### 5.1. このドキュメントの役割

開発履歴は、プロジェクトで実施した作業を時系列で記録するドキュメントです。
「**何をいつやったか**」を記録し、将来の参照や問題発生時の原因調査に使います。

### 5.2. 内容の解説

本文書は非常に長く（262行）、詳細な記録が残されています。

#### （1）フェーズ別実施記録

各フェーズごとに表格で記録されています。

```
### 2.1 Step1: 仕様の根拠となる情報の収集 (2026-08-17)
| 項目 | 内容 |
|------|------|
| 実施内容 | step0100_constitution.md の作成 |
| 成果物 | `step0100_constitution.md` |
| 技術スタック | C# .NET 8.0, WPF, MVVM ... |
```

**初心者へのヒント**: なぜ開発履歴を書くのか？

- **問題発生時の原因調査**: 「いつ」「何を」変更したかが分かる
- **新人への引き継ぎ**: 新しいメンバーが「プロジェクトの経緯」を理解できる
- **納品時の説明資料**: お客様や上司に「どんな開発をしたか」を説明できる

#### （2）テスト結果一覧

テストの結果も開発履歴に記録されています。

```
| テストクラス | ファイルパス | 件数 | 状態 |
|-------------|------------|------|------|
| CartItemViewModelTests | ViewModels/ViewModelTests.cs | 9件 | PASS |
| MainViewModelTests | ViewModels/ViewModelTests.cs | 25件 | PASS |
```

#### （3）ファイル構成

プロジェクトのファイル構成も開発履歴に記録されています。
これは「どんなファイルがあるか」を一覧化するものです。

### 5.3. 自分で書く場合のポイント

- **日付を必ず書く**: いつやったかが分かるようにする
- **成果物を具体的に**: 「做了」ではなく「`step0200_spec.md` を作成」のようにファイル名まで書く
- **テスト結果も記録する**: テスト件数、パス/フェイル、カバレッジ
- **フェーズごとに区切る**: 読みやすさのために段落を分ける

## 第6章: Step2 ― 要件定義書（step0200_spec.md）

### 6.1. このドキュメントの役割

要件定義書は「**なぜこのシステムが必要で、何ができるようになるか**」を定義するドキュメントです。
技術的な内容は書かず、業務観点での要件を書きます。

### 6.2. 内容の解説

#### （1）プロジェクト概要

```
| プロジェクト名 | コンビニPOSシステム MVP |
| バージョン | 1.0 |
| 作成日 | 2026-08-18 |
```

**初心者へのヒント**: 「MVP」とは？

MVPとは「Minimum Viable Product（実用最小限の製品）」の略です。
「最低限これだけ作れば、ユーザーに使ってもらえる」水準の機能のことです。

たとえば、コンビニPOSシステムのMVPなら：
- 商品スキャン → OK
- 会計計算 → OK
- レシート出力 → OK
- クレジットカード決済 → MVP対象外（将来の機能）
- 在庫管理 → MVP対象外（将来の機能）

#### （2）ステークホルダー

```
| 役割 | 担当 | 責務 |
|------|------|------|
| プロジェクトオーナー | （未定） | 最終承認、予算管理 |
| 業務オーナー | （未定） | 業務要件の定義、受け入れ判定 |
```

**初心者へのヒント**: ステークホルダーとは？

ステークホルダーとは、プロジェクトに利害関係を持つすべての人です。
「開発する人」だけでなく、「使う人」「お金を出す人」「運営する人」を含みます。

#### （3）目的と課題

```
### 1.2. 目的
コンビニ店舗でのレジ業務をデジタル化し、商品スキャンから会計確定・レシート出力までの
基本的なPOS操作を実現する。

### 1.3. 解決する課題
- 手計算による会計ミスの防止
- 税率の正確な適用と集計
- 取引データの自動DB保存による業務効率化
- レシート自動出力による紙面業務の削減
```

**初心者へのヒント**: Whyを先に書く

「なぜこのシステムを作るのか」を先に書くことで、関係者の認識を揃えます。
「え、これ必要だったの？」という問題を防ぐことができます。

#### （4）受け入れ基準（AC）

```
| AC-1 | バーコード入力で既存商品が正しくカートに追加されること |
| AC-2 | 同一商品を2回スキャンした場合、数量が2になること |
| AC-3 | 存在しないJANコード入力時にエラーが表示されること |
```

**初心者へのヒント**: 受け入れ基準（Acceptance Criteria）とは？

受け入れ基準は「**これができたら完成**」という判定基準です。
テストの「期待結果」に相当します。

受け入れ基準を書く時のコツ：
1. **具体的に書く**: 「正しく計算される」→「`Floor(単価 × 数量 × 1.08)` で計算される」
2. **番号をつける**: AC-1, AC-2, ... のようにIDをつける
3. **例外も書く**: 正常系だけでなく、異常系（存在しないJANコードなど）も書く

#### （5）スコープ外

```
| 支払方法選択（クレジット/電子マネー） | MVPは現金のみ |
| 在庫管理・売上レポート | MVPは取引記録に集中 |
```

**初心者へのヒント**: スコープ外を書く重要性

「何をやらないか」を明確にすることで、「何に集中するか」が明確になります。
「あれもこれもやりたい」となると、納期遅延や品質低下につながります。

### 6.3. 自分で書く場合のポイント

- **Why → What の順で書く**: まず「なぜ必要か」、次に「何ができるようになるか」
- **受け入れ基準は13個まで**: あまり多いと管理が難しい。優先度の高いものだけ抽出する
- **スコープ外は必ず書く**: 「やらないこと」の明確化は「やること」の明確化と同じくらい重要
- **技術的な内容は書かない**: 要件定義書は「業務観点」のドキュメントです。技術的な実装方法はstep0300以降で書きます

## 第7章: step0201_business_rules.md（業務ルール詳細書）

### 7.1. このドキュメントの役割

業務ルール詳細書は、要件定義書では書けなかった「**計算式や条件分岐の詳細**」を定義するドキュメントです。

### 7.2. 内容の解説

#### （1）番号付きルール定義

```
### BR-020: 税込小計計算（商品単位）
- `LineTotalWithTax = Math.Floor(UnitPrice × Quantity × (1 + TaxRate / 100))`
- **端数処理: すべて切り捨て（Floor）**
- 計算順序: まず単価×数量、次に税率適用、最後にFloor
```

**初心者へのヒント**: なぜ番号をつけるのか？

ルールに番号（BR-020）をつけることで、以下のメリットがあります。

- **参照が容易**: 「BR-020の計算式は？」とピンポイントで参照できる
- **変更管理**: 「BR-020を修正しました」と報告できる
- **トレーサビリティ**: 「どのルールがどのテストで検証されているか」を追跡できる

#### （2）計算例

```
【例1: 8%商品のみ】
おにぎり梅 ¥120 (8%) × 2個
LineTotalWithTax = Floor(120 × 2 × 1.08) = Floor(259.2) = 259
```

**初心者へのヒント**: 計算例を書くメリット

計算例を書くことで、開発者が「本当にこの計算で合っているか」を確認できます。
テストケースの基準にもなります。

#### （3）禁止事項

```
| P-001 | 税率の合算後Floor処理 | 日本消費税法に違反 |
| P-002 | 負数の数量入力 | 業務上不正なデータ |
```

**初心者へのヒント**: 「やってはいけないこと」を書くメリット

「やってはいけないこと」を明確にすることで、開発者の判断ミスを防げます。
特に法律に触れるような問題は、明確に禁止事項として定義すべきです。

### 7.3. 自分で書く場合のポイント

- **ルールごとに番号をつける**: BR-001, BR-002, ... のように
- **計算式は数式で書く**: プログラミング言語ではなく、数式として書く
- **計算例を最低1つは書く**: 設計者が意図した計算かどうかの確認に使う
- **禁止事項も番号をつけて定義する**: P-001, P-002, ... のように

## 第8章: step0202_process_flow.md（業務フロー図）

- **編集が簡単**: ツールに依存しない

### 9.1. このドキュメントの役割

非機能要件書は「**動くこと以外の品質**」を定義するドキュメントです。

## 第14章: step0208_service_architecture.md（サービスアーキテクチャ）

### 14.1. このドキュメントの役割

サービスアーキテクチャは、**サービス層の設計方針**を定義するドキュメントです。

### 14.2. 内容の解説

#### （1）なぜサービス層を分離するのか

```
- テスト容易性: DBアクセスを抽象化し、単体テストでモックを使用できる
- 責務分離: ViewModel はUIロジックと計算に専念し、DB操作はサービス層が担当
- 将来拡張性: サービス実装を変更してもViewModelに影響しない
```

**初心者へのヒント**: サービス層とは？

サービス層は、ViewModelとデータベースの間に位置する層です。
「バーコードで商品を検索する」「取引を保存する」といったDB操作を担当します。

なぜ分離するのか？

- **テストしやすさ**: DBに接続しなくてもテストできる
- **保守しやすさ**: DB操作の変更がViewModelに影響しない
- **再利用性**: 別のViewModelからも同じサービスを使える

#### （2）DI（依存関係の注入）

```
services.AddSingleton<IBarcodeService, BarcodeService>();
services.AddSingleton<ITransactionService, TransactionService>();
```

**初心者へのヒント**: DIとは？

DI（Dependency Injection：依存関係の注入）とは、
「必要なものを外から渡す」仕組みです。

たとえば、MainViewModelがBarcodeServiceを使いたい場合：
- **DIなし**: MainViewModelが自分でBarcodeServiceを生成する
- **DIあり**: 外部（DIコンテナ）がBarcodeServiceを生成してMainViewModelに渡す

DIがあるメリット：
- **テストしやすい**: テスト用のモックを渡せる
- **変更しやすい**: サービスの実装を変えてもViewModelを変えなくていい

### 14.3. 自分で書く場合のポイント

- **「なぜ分離するのか」を明確に**: 技術的な理由を業務的な言葉で説明する
- **インターフェース定義を書く**: どんなメソッドがあるかを明確に
- **データフロー図を書く**: データがどこからどこへ流れるかを図示する
- **テストカバレッジも書く**: テストの対象範囲を明確にする

```
### 3.1. Model層テスト
| テスト対象 | テスト内容 |
|------------|-----------|
| Product デフォルト値 | JanCode が string.Empty で初期化されること |

### 3.2. ViewModel層テスト
| テスト対象 | テスト内容 |
|------------|-----------|
| LineTotal 計算 | UnitPrice * Quantity が正しく計算されること |
```

**初心者へのヒント**: テスト戦略のポイント

- **フレームワークを決める**: xUnit, NUnit, MSTest など
- **カバー対象を決める**: 何をテストし、何をテストしないか
- **モックの使用方針**: DB接続はどうするか

#### （3）テストカバレッジ対象外

```
| PosDbContext | インテグレーションテストの対象 |
| MainWindow | UI テストの対象 |
```

**初心者へのヒント**: 「何をテストしないか」も書く

「何をテストするか」だけでなく、「何をテストしないか」も明確にします。
テスト対象が広すぎると、テストコストが膨大になります。

### 17.3. 自分で書く場合のポイント

- **フレームワークとツールを明記する**: 何を使ってテストするか
- **カバー対象と非対象を明確にする**: テストのスコープを決める
- **テスト件数の目標を書く**: 「○件以上」のように具体的に

## 第18章: step0303_testplan.md（テスト計画書）

### 18.1. このドキュメントの役割

テスト計画書は、テスト戦略に基づく**具体的な実行計画**を定義するドキュメントです。

### 18.2. 内容の解説

#### （1）テスト進入条件（Entry Criteria）

```
| EC-1 | テストプロジェクトが正常にビルドできること |
| EC-2 | xUnit / Moq / coverlet が正常にインストールされていること |
```

**初心者へのヒント**: 進入条件とは？

進入条件は「**テストを開始する前に満たなければならない条件**」です。
「テストプロジェクトがビルドできない状態でテストを実行しても意味がない」ことを防ぎます。

#### （2）テスト完了条件（Exit Criteria）

```
| XC-1 | 全テスト件数がパスすること | 100%パス |
| XC-2 | ViewModel層のカバレッジ | 80%以上 |
```

**初心者へのヒント**: 完了条件とは？

完了条件は「**テストを終了して良い条件**」です。
「テストが少しパスしたから終わり」ではなく、「全件パスし、カバレッジも達成して初めて終わり」と定義します。

### 18.3. 自分で書く場合のポイント

- **進入条件と完了条件を明確に**: 「いつ始めていいか」「いつ終わっていいか」
- **具体的な数値を書く**: 「80%以上」「30秒以内」のように
- **手動テストも計画に含める**: 自動化できないテストもある

## 第19章: step0304_deployment.md（運用・配置計画）

### 19.1. このドキュメントの役割

運用・配置計画は、システムの**インストールから運用まで**の手順を定義するドキュメントです。

### 19.2. 内容の解説

#### （1）動作環境要件

```
| OS | Windows 10 (1809以降) または Windows 11 |
| .NETランタイム | .NET 8.0 Desktop Runtime |
| データベース | SQL Server LocalDB |
```

#### （2）障害対応フロー

```
| Level 1 | アプリケーションが起動しない | .NET Runtime の再インストール |
| Level 2 | 商品追加ができない | JANコードの確認、DB接続確認 |
| Level 3 | レシートが出力されない | デスクトップの書き込み権限確認 |
```

**初心者へのヒント**: 運用計画を書くメリット

「開発は終わったが、どう動かせばいいか分からない」という問題を防ぎます。
納品時に「これは運用手順書です」と一緒に渡すことで、納品の Completeness が上がります。

### 19.3. 自分で書く場合のポイント

- **環境要件を具体的に**: OS、ランタイム、DBなど
- **インストール手順はステップバイステップで**: 1つずつ書く
- **障害対応フローを分類する**: 障害レベル別に対応を書く

## 第20章: step0305_risk_register.md（リスクレジスター）

### 20.1. このドキュメントの役割

リスクレジスターは、プロジェクトの**リスクを識別・評価・管理**するドキュメントです。

### 20.2. 内容の解説

#### リスク評価基準

```
### 発生可能性
| 高 | 50%以上の確率で発生する |
| 中 | 25%〜50%の確率で発生する |
| 低 | 25%未満の確率で発生する |

### 影響度
| 高 | 納品遅延、データ損失、法的問題を引き起こす |
| 中 | 機能制限、品質低下を引き起こす |
```

#### リスク一覧

```
| R-004 | セキュリティ | 認証機能なし | 高 | 高 | 高 | MVP後迅速にログイン機能を実装 |
| R-005 | セキュリティ | DB接続文字列の漏洩 | 低 | 高 | 中 | appsettings.json を Git 管理対象外に設定 |
```

**初心者へのヒント**: リスクを「書く」ことの効果

リスクを文書化することで、「想定していなかった問題」の発生確率が下がります。
「あ、これ Risksに書いてあったな」と想起できるからです。

### 20.3. 自分で書く場合のポイント

- **評価基準を先に定義する**: 何が「高」で何が「低」か
- **リスクを具体的に書く**: 「技術的課題」ではなく「EF Core マイグレーション失敗」
- **対策も一緒に書く**: リスクだけ書いて対策がないのは意味がない

## 第21章: step0306_uat_plan.md（UAT計画）

### 21.1. このドキュメントの役割

UAT（User Acceptance Test：ユーザー受入テスト）計画は、**ユーザー視点での最終テスト**の計画です。

### 21.2. 内容の解説

#### UATシナリオ

```
### S-001: 商品スキャン基本操作
| 手順 | 1. バーコード「777777」を入力 → Enter |
| 期待結果 | おにぎり梅（¥120、8%）がカートに追加される |
| 対応AC | AC-1 |
```

**初心者へのヒント**: UATと単体テストの違い

- **単体テスト**: 開発者が「コードが正しく動くか」を検証する
- **UAT**: ユーザー（またはユーザー代表）が「業務要件を満たすか」を検証する

単体テストは「正しく動くか」、UATは「使い物になるか」を検証します。

### 21.3. 自分で書く場合のポイント

- **シナリオは具体的に**: 「バーコード777777を入力」のように具体的な値を書く
- **期待結果も具体的に**: 「正しく計算される」→「¥259になる」
- **対応ACを書く**: どの要件に対応するテストかを明確にする

## 第22章: step0307_rollback_procedures.md（ロールバック手順）

### 22.1. このドキュメントの役割

ロールバック手順は、**デプロイ失敗時に元に戻す**手順を定義するドキュメントです。

### 22.2. 内容の解説

#### ロールバック手順の例

```bash
# 1. 実行中のアプリを終了
taskkill /F /IM ConveniencePos.exe

# 2. バックアップフォルダから前バージョンを復元
xcopy /E /Y "C:\Backup\ConveniencePos\v1.0" "C:\Program Files\ConveniencePos\"
```

**初心者へのヒント**: ロールバック手順を書くメリット

「デプロイしてみたが、動かない。どう戻せばいいか分からない」という事態を防ぎます。
ロールバック手順は「保険」のようなものです。書いておいて損はありません。

### 22.3. 自分で書く場合のポイント

- **コマンドを具体的に書く**: 実際に実行できるコマンドを書く
- **バックアップ手順も書く**: ロールバックの前提となるバックアップ方法
- **復旧目標を書く**: RPO（どれくらいのデータが失われて許容か）、RTO（どれくらいで復旧するか）

## 第23章: step0308_data_dictionary.md（データ辞書）

### 23.1. このドキュメントの役割

データ辞書は、データベースの**全テーブル・カラムの正式な定義**を定義するドキュメントです。

### 23.2. 内容の解説

#### テーブル定義

```
## 3. Products（商品マスタ）

| カラム名 | データ型 | NULL可否 | 制約 | 説明 |
|----------|---------|---------|------|------|
| Id | int | NOT NULL | PRIMARY KEY, IDENTITY | 商品ID |
```

**初心者へのヒント**: データ辞書の重要性

データ辞書は「データベースの教科書」です。
開発者が「このカラムはどんな型で、何の制約があるか」を確認するのに使います。

### 23.3. 自分で書く場合のポイント

- **全カラムを網羅する**: 漏れなく書く
- **制約を明記する**: PRIMARY KEY, FOREIGN KEY, UNIQUE, CHECK など
- **リレーション図も書く**: テーブル間の関係を図示する
- **シードデータも書く**: 初期データの一覧

## 第24章: step0309_traceability_matrix.md（トレーサビリティ行列）

### 24.1. このドキュメントの役割

トレーサビリティ行列は「**要件とテストの対応関係**」を明確にするドキュメントです。

### 24.2. 内容の解説

#### トレーサビリティ行列

```
| AC ID | 受け入れ基準 | 対応テストクラス | テストメソッド | 状態 |
|-------|-------------|-----------------|---------------|------|
| AC-1 | バーコード入力で商品が追加される | MainViewModelTests | Subtotal_SingleItem_ReturnsCorrectValue | パス |
| AC-4 | 軽減税率計算 | CartItemViewModelTests | LineTotalWithTax_TaxRate8_CalculatesCorrectly | パス |
```

**初心者へのヒント**: トレーサビリティとは？

トレーサビリティとは「追跡可能性」のことです。
「このテストはどの要件に対応しているか」「この要件はどのテストで検証されているか」を
追跡できるようにするものです。

これにより：
- **テスト漏れがないか**: 「この要件に対応するテストがあるか」が分かる
- **変更影響分析**: 「この要件を変えたら、どのテストを直す必要があるか」が分かる

### 24.3. 自分で書く場合のポイント

- **全ACを網羅する**: 1つのACでも漏れがあってはいけない
- **対応テストを具体的に**: テストクラス名、メソッド名まで書く
- **状態を記録する**: パス/フェイル/未テスト

## 第25章: Step4 ― タスク管理リスト（step0400_tasks.md）

### 25.1. このドキュメントの役割

タスク管理リストは、実装すべき作業を**細かいチェックリストに分解**したドキュメントです。

### 25.2. 内容の解説

#### フェーズ別タスク分解

```
## フェーズ1: データベースとモデルの構築
- [X] Task 1.1: EF Coreのデータモデルクラスを作成する
- [X] Task 1.2: PosDbContext を作成し、SQL Serverへの接続設定を行う

## フェーズ2: ロジックとViewModelの実装
- [X] Task 2.1: BarcodeService を作成し、DI 注入する
- [X] Task 2.2: MainViewModel を作成する
```

**初心者へのヒント**: タスク分解のポイント

1. **1タスク = 1つの具体的な作業**: 「システムを構築する」→「Productクラスを`Models/`に作成する」
2. **チェックボックスをつける**: 完了/未完了が一目で分かる
3. **依存関係に従って順番に書く**: 先にDBを作らないとViewModelが作れない
4. **ファイル名まで書く**: 「`Models/Product.cs`を`Models/`フォルダに作成する」

### 25.3. 自分で書く場合のポイント

- **1タスクは15分〜1時間で完了できる粒度に**: 大きすぎるタスクは分解する
- **チェックボックスをつける**: 完了状況が一目で分かるように
- **フェーズごとに区切る**: 構造を明確にする
- **テストタスクも含める**: 「テストを書いてパスすることを確認」もタスクにする

## 第26章: 仕様書を書く前の準備

### 26.1. まず「なぜ」を考える

仕様書を書く前に、以下の問いに答えてみましょう。

1. **誰のために作るのか？**: ターゲットユーザーは誰か
2. **何を解決するのか？**: どんな課題があるのか
3. **完成したらどうなるか？**: 理想の状態はどんな状態か

### 26.2. 情報を収集する

- **既存のシステムがある場合**: 既存システムの仕様書、マニュアル、ユーザーの声
- **新規開発の場合**: 類似システムの調査、ユーザーインタビュー、市場調査
- **技術調査**: 使える技術、制約条件、チームのスキル

### 26.3. ドキュメント構成を決める

本プロジェクトのような4ステップ構成を採用する場合：

```
step0100: プロジェクト憲法（技術スタック、コード規約）
step0200: 要件定義（Why + What）
  ├── step0201: 業務ルール
  ├── step0202: 業務フロー
  ├── step0203: 非機能要件
  ├── step0204: UI設計
  └── step0205〜: 機能拡張
step0300: 技術計画（How）
  ├── step0301: 技術計画詳細
  ├── step0302: テスト戦略
  ├── step0303: テスト計画
  └── step0304〜: 補助ドキュメント
step0400: タスク分解
```

## 第27章: 仕様書の書き方ルール

### 27.1. 共通ルール

1. **表格を使う**: 情報を整理して見せる
2. **番号をつける**: AC-1, BR-010, R-005 のように
3. **簡潔に書く**: 1行に1情報を
4. **具体的に書く**: 「適切に」→「80%以上」
5. **参照先を明記する**: 他ドキュメントへの参照

### 27.2. 段落構成

すべての仕様書に共通する段落構成：

```
# ドキュメント名

## 1. ドキュメント概要
（表格: バージョン、作成日、役割、関連ドキュメント）

## 2. 本題
（ドキュメントごとの内容）

## バージョン履歴
（表格: バージョン、変更日、変更内容、変更者）

## 承認記録
（表格: 役割、氏名、承認日、署名）
```

### 27.3. 段落構成の理由

- **ドキュメント概要**: 「何のドキュメントか」を最初に説明する
- **本題**: 実際の内容
- **バージョン履歴**: 変更管理
- **承認記録**: 誰が承認したか

### 27.4. マークダウン記法の使い方

仕様書はMarkdown形式で書きます。よく使う記法：

```markdown
# 見出し1
## 見出し2
### 見出し3

| カラム1 | カラム2 |
|---------|---------|
| 値1 | 値2 |

- 箇条書き
- 箇条書き

**太字**
*斜体*

`コード`
```

# 第4部: よくある質問とコツ

---

## 第29章: 初心者がつまづきやすいポイント

### Q1: 仕様書はどれくらいの長さにすべきか？

**A**: 目安はありません。重要なのは「内容が網羅的かどうか」です。
しかし、初心者によくある失敗は「短すぎて情報が不足している」ことです。
最初は詳しく書き、慣れてから簡潔に書けるようになりましょう。

### Q2: 仕様書を書くのが面倒な場合はどうすればいいですか？

**A**: 仕様書は「書くもの」ではなく「作るもの」と考えましょう。
設計図を書くことが工事の一部であるように、仕様書を書くことも開発の一部です。

### Q3: 仕様書は誰に読ませるのか？

**A**: 主な読者は以下の通りです。

- **開発者**: 「何を作ればいいか」を理解する
- **テスト担当者**: 「何をテストすればいいか」を理解する
- **プロジェクトマネージャー**: 「進捗をどう把握するか」に使う
- **将来の自分**: 「6ヶ月後に見返しても理解できるか」
- **納品先**: 「何が欲しいのか」の合意確認

### Q4: 仕様書は一度書いたら終わりか？

**A**: いいえ。仕様書は生きたドキュメントです。
仕様が変わった場合は、上流から修正します。

```
step0200（要件定義）を変更した場合
  → step0300（技術計画）も変更
    → step0400（タスク）も変更
```

### Q5: AIが仕様書を書いてくれるのか？

**A**: AIは仕様書の「ドラフト（案）」を書くことはできます。
しかし、最終的なレビューと承認は人間が行います。
AIは「書く手助け」であり、「責任の転嫁先」ではありません。

### Q6: 仕様書とドキュメントの違いは？

**A**: 本質的には同じです。ただし、本プロジェクトでは以下の使い分けをしています。

- **仕様書（spec）**: 「何を作るか」「どう作るか」を定義する
- **ドキュメント（doc）**: 仕様書以外の情報（マニュアル、ガイドなど）

### Q7: 矛盾がある場合はどうするか？

**A**: 仕様書間に矛盾がある場合は、上流の仕様書を正とします。

```
step0200（要件定義） > step0300（技術計画） > step0400（タスク）
```

たとえば、step0200で「税率は8%と10%」と書いてあるのに、
step0301で「税率は8%のみ」と書いてあれば、step0301を修正します。

## 第30章: 仕様書を書く上でのコツ

### 30.1. 「5W1H」で書く

すべての記述に5W1Hを当てはめましょう。

- **Who**: 誰が使うか
- **What**: 何をするか
- **Where**: どこで使うか
- **When**: いつ使うか
- **Why**: なぜ必要か
- **How**: どうやってやるか

### 30.2. 「具体的に」書く

| 悪い例 | 良い例 |
|--------|--------|
| 速い処理をする | 500ms以内に処理する |
| 正しく計算する | `Floor(単価 × 数量 × 1.08)` で計算する |
| エラー時に表示する | 「商品が見つかりません (JAN: {入力値})」と表示する |

### 30.3. 「表格」を活用する

表格は情報を整理して見せる最適な手段です。
以下の場面で表格を使いましょう。

- プロパティ一覧
- テストケース一覧
- リスク一覧
- 要件一覧

### 30.4. 「図」を活用する

フローチャート、状態遷移図、ER図は、テキストだけでは伝わりにくい情報を
視覚的に伝えるのに有効です。

### 30.5. 「簡潔に」書く

1行に1情報を。長文は避けましょう。
冗長な説明は「附録」に追い出すか、別ドキュメントに書きます。

## 付録A: 専門用語集

| 用語 | 説明 |
|------|------|
| **仕様書（スペック）** | システムの機能や動作を文書化したもの |

| **外部設計** | ユーザーから見たシステムの設計 |
| **内部設計** | 開発者から見たシステムの設計 |

| **MVVM** | Model-View-ViewModel。画面・データ・ロジックを分離するパターン |

| **CRUD** | Create, Read, Update, Delete。データの基本操作 |

| **カバレッジ** | テストでカバーされているコードの割合 |
| **トレーサビリティ** | 要件からテストまでを追跡できる状態 |
| **ロールバック** | 失敗した変更を元に戻すこと |
| **RPO** | Recovery Point Objective。復旧ポイント目標 |
| **RTO** | Recovery Time Objective。復旧時間目標 |
| **UAT** | User Acceptance Test。ユーザー受入テスト |
